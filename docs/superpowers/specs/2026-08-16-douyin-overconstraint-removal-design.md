# 抖音媒体提取过度约束移除设计

## 背景与证据

现有项目记录中没有发现“用户提交作品 A，插件实际转写了推荐作品 B”的真实线上事故。相关限制来自开发阶段的风险推测和合成测试：抖音页面会同时加载多个媒体，因此代码逐步增加了“唯一作品身份”“多个无身份播放器拒绝”“混合身份拒绝”“没有稳定 aweme ID 就失败关闭”等门槛。

真实线上失败反而集中在详情接口空壳、页面跳转后 ID 丢失、目标播放器缺少身份属性，以及身份门槛把已经可播放的媒体拒绝。`1.3.30` 的工作方式是精确详情优先，失败后直接使用当前页面可播放媒体；它没有上述失败关闭门槛。

## 目标行为

1. 结构化详情、目标 aweme 响应和已认证会话仍然优先，成功时直接使用。
2. 精确通道失败后，隐藏浏览器按“正在播放、视口可见、面积、DOM 顺序”选择最强的当前页面媒体。
3. 作品 ID 只作为排序加分，不再作为候选媒体的失败门槛。
4. 推荐标签、混合身份、缺少唯一页面身份、多个无身份播放器、缺少稳定 aweme ID 都不得单独导致失败。
5. 仅当浏览器最终地址明确包含另一个具体作品 ID 时拒绝；通用首页、空 canonical、canonical 中的预加载身份不构成拒绝证据。
6. 诊断继续保留解析阶段和失败原因，但诊断标签不能反过来成为产品阻断条件。

## 范围

- 修改插件发布权威源 `obsidian-plugin/wechat-inbox-sync/src/main.js`，并重新生成 bundle。
- 更新抖音媒体选择回归测试。
- 更新长期决策、发布检查规则和事故案例日志。
- 不改版本号，不发布，不部署，不触碰 CloudBase、绑定码、Pro、支付或用户数据。

## 验收

- 精确详情媒体仍优先。
- 当前页面有可播放媒体时，混合身份、外部候选身份、多个无身份播放器和缺少 aweme ID 均可继续提取。
- 明确跳转到另一个 `/video/:id` 的页面仍拒绝。
- 源码测试、生成 bundle 测试、完整插件回归、语法、构建漂移和 diff 检查通过。
