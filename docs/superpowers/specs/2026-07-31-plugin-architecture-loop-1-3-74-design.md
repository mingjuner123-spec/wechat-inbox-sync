# 插件架构重构 Loop 设计

## 1. 背景

当前正式插件 1.3.74 的 `main.js` 已超过两万行，同时承载本地组件、网页解析、浏览器会话、Markdown 转换、同步编排和设置 UI。大文件本身不是错误，但它让每次修改的定位、测试和发布范围过大，也容易在不同本地候选之间发生覆盖或功能回退。

此前已经在 1.3.71 上验证过“单一源码、确定性打包、逐模块抽离”的可行性。然而 1.3.71 之后又新增了 macOS ASR 修复、小红书图片去重、行为恢复和失败记录清理。旧模块化分支不能整体合回，否则会确定性丢失 1.3.72–1.3.74 的功能。

本设计以 `f08429ed` 为唯一基线。该提交包含 1.3.74 正式业务代码，以及本地完成、独立终审通过的发布候选 V2 管线。

## 2. 方案选择

### 方案 A：从当前稳定基线逐模块向前移植（采用）

- 从 1.3.74 当前 `main.js` 建立 `src/main.js`。
- 适配固定版本 esbuild，生成仍可由 Obsidian 直接加载的单文件 `main.js`。
- 历史模块和测试只作 donor；每个函数从当前源码重新提取。
- 每次只完成一个模块，通过完整回归和独立审查后固化。

优点：保留最新功能，回退边界最小，能够复用历史验证。缺点：比直接合并慢，但风险可控。

### 方案 B：整体合并 1.3.71 模块化分支（拒绝）

会覆盖 1.3.72–1.3.74 的小红书与 ASR 修复，并与新的候选、镜像和 Release 契约冲突。

### 方案 C：完全忽略历史成果，从零设计（拒绝）

可以避免继承旧假设，但会浪费已经独立审查过的模块边界、测试语料和构建经验。

## 3. 目标架构

```text
obsidian-plugin/wechat-inbox-sync/
├─ src/
│  ├─ main.js
│  ├─ utils/
│  ├─ core/
│  ├─ storage/
│  ├─ parsers/
│  ├─ local-components/
│  └─ ui/
├─ build-plugin.js
├─ main.js
├─ manifest.json
├─ versions.json
└─ styles.css
```

第一阶段不会一次建立全部目录，也不会搬动高风险职责。目录随经过验证的模块逐步出现。

## 4. 单文件发布约束

Obsidian 市场可靠加载的是插件目录中的单一 `main.js`。`src/*` 只用于开发和测试，正式 `main.js` 必须由固定版本构建器打包，并继续把 `obsidian` 标为 external。运行时不能依赖未随市场分发的散文件。

构建必须满足：

- 相同输入连续构建字节一致。
- `--check` 只读比较生成结果与已提交 `main.js`。
- 失败时不留下半写文件。
- 新候选管线从已验证的生成物制作候选，不从另一套可变工作区重组。
- 根目录市场镜像继续由 V2 管线单向生成，不删除。

## 5. 模块迁移策略

### 批次 0：构建边界

把当前 1.3.74 `main.js` 原样作为 `src/main.js`，调整构建包装使初始生成物与基线行为等价。首批不抽任何业务函数。

### 批次 1：低风险纯函数

按顺序处理日期、转写质量、进度提示、AI 元数据错误、诊断脱敏、Vault 路径和输入规范化。

### 批次 2：记录契约

处理记录元数据、记录状态、记录身份。它们会影响重复笔记、跳过和失败分类，因此后置并加入状态矩阵和差分测试。

### 批次 3：用户验收后再设计

Frontmatter、附件存储、同步状态机、平台解析器和设置 UI 不在第一阶段实施范围。先依据第一阶段的真实收益和用户测试结果重新设计。

## 6. 不变式

- 版本保持 1.3.74。
- 小红书、ASR/OCR、同步队列和双环境行为不变。
- 所有现有用户设置键、默认值和保存格式不变。
- 所有笔记路径、文件名、frontmatter、正文、附件和提示语不变。
- `data.json` 不进入构建、候选或测试快照。
- 当前线上、GitHub 和插件市场不发生任何写入。

## 7. Harness 与长期记忆

任务卡记录权限、边界和停止条件；本设计记录为什么选择向前移植；实施计划记录每个检查点；代码地图记录当前结构和已完成模块；Worklog 只记录阶段结果；Git 提交是可执行回退点。

每次上下文恢复时只需按顺序读取：

1. `AGENTS.md`
2. 本任务卡
3. 本设计
4. 实施计划中的当前检查点
5. `docs/PLUGIN_CODE_MAP_1.3.74.md`
6. `git status` 与最近提交

不依赖聊天上下文恢复工程状态。

## 8. 审查模型

- 主 Agent 负责设计、实现、验证和检查点。
- 子 Agent 在每个有行为影响风险的模块完成后做独立审查。
- 构建地基和整分支必须做规格与质量终审。
- 任何审查发现都先验证证据，再通过失败测试修复；不为“保险”增加无需求的防护。

## 9. 发布边界

本任务的终点是本地候选和人工测试清单。负责人测试通过后，另建 L3 发布任务，重新采样候选提交并执行发布管线。重构任务本身没有发布授权。
