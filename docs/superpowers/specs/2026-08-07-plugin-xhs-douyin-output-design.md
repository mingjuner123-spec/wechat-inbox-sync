# 小红书视频与抖音结构化输出设计

## 目标

本次只制作本地测试版，不发布、不部署、不修改用户配置。需要同时完成：

1. 小红书视频笔记固定按“标题 → 正文 → 标签 → 封面 → 视频文案转写 → 评论区”输出。
2. 小红书评论区主评论与楼中楼回复合计最多 1000 条；来源不足或到达既有时间预算时保存已取得内容，不让评论抓取阻塞整篇同步。
3. 抖音不再只依赖通用网页 meta 标签，而是从与目标作品 ID 匹配的结构化作品对象中一次性提取标题、原文、标签、封面、媒体地址和互动数据。
4. 抖音最终正文按“标题 → 原文正文 → 标签 → 封面 → 视频文案转写”输出；播放、点赞、收藏、评论、分享数继续写入 Obsidian 笔记属性。

## 根因

现有抖音链路已经能够从移动分享页或详情接口的结构化作品对象中取得目标媒体地址，也会尝试读取互动指标；但标题、正文、标签和封面仍主要通过普通网页的 `og:*`/`description` 标签生成。实际移动分享页不保证暴露这些通用标签，因此会出现“媒体可以转写，但原始内容和数据属性缺失”的半套结果。

小红书视频当前把评论区直接包含在转写前的补充 Markdown 中，转写正文随后由通用转写渲染器追加，导致评论区出现在视频文案之前。

## 设计

### 1. 统一的抖音作品内容模型

新增纯解析边界，将与目标 `aweme_id` 匹配的作品对象规范化为：

- `title`：优先平台明确标题；否则使用作品原始文案的首个有效标题行，不使用 AI 虚构标题。
- `description`：保留平台原始作品文案。
- `tags`：优先读取结构化话题/挑战字段，同时补充原文中的 `#标签`，去重后输出。
- `coverUrl`：优先使用作品视频的静态封面，再使用动态封面或通用网页封面兜底。
- `mediaUrls`：沿用当前与目标作品 ID 绑定的媒体地址选择逻辑。
- `socialMetrics`：读取同一作品对象中的播放、点赞、收藏、评论和分享数。

数据优先级为：目标作品结构化对象 → 目标作品详情接口 → 通用网页 meta。不得从推荐流中的其他作品补字段，也不得用 AI 伪造平台原始信息。

### 2. 抖音渲染

结构化内容先进入现有统一社媒补充 Markdown 构建器，再交给转写渲染器。最终顺序为：

1. 标题
2. 原文正文
3. 标签
4. 封面图
5. 视频文案转写

互动数据仍进入 YAML 笔记属性，不在正文中重复展示。字段不存在时只省略该字段，不让同步失败。

### 3. 小红书视频评论后置

小红书正文解析继续负责标题、正文、标签和图片；评论 Markdown 从视频转写前的补充 Markdown 中独立出来。视频转写成功或失败后，统一渲染层再把评论区追加到正文末尾。图文笔记维持现有评论末尾行为。

### 4. 评论上限与停止条件

- 主评论与楼中楼回复共用 1000 条总预算。
- 单个楼层回复仍受单楼层上限保护，避免某个热门楼层独占全部时间。
- 页面数量上限随总预算调整，但继续受现有请求/时间预算约束。
- 达到 1000 条、来源耗尽或时间预算到达时，返回当前已取得评论和停止原因；不得将整篇同步判为失败。

## 回归测试

必须先新增会失败的测试，再实现代码：

1. 小红书视频正文断言评论区位于视频文案之后。
2. 评论树主评论与回复合计最多 1000 条，且超量时截断为 1000。
3. 评论分页在来源不足或预算结束时返回部分结果而非同步失败。
4. 使用接近真实 `window._ROUTER_DATA` 形状的抖音夹具，断言结构化标题、原文、标签、封面、媒体地址和互动指标都来自同一 `aweme_id`。
5. 抖音最终 Markdown 顺序和 YAML 数据属性完整。
6. 推荐流中存在其他作品时，不得串用其他作品的封面、文案或数据。
7. 现有小红书图文、B站、小宇宙、ASR 兼容和重复转写回归保持通过。

## 本地替换安全

构建完成后仅替换用户插件目录中的 `main.js`、`manifest.json`、`styles.css`、`versions.json`。替换前后必须比较 `data.json` 哈希、绑定数量和绑定令牌指纹；任何变化都立即停止并恢复程序文件。插件版本仍作为本地 1.3.76 测试候选，不创建 Release。
